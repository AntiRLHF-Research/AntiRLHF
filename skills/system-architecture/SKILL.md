# 系统架构

## 从完整产品行为设计

读取用户要完成的能力和现有真实入口。新项目先选一条核心操作链：输入怎样进入、谁作业务决定、状态怎样改变、外部效果怎样发生、使用者怎样得到结果。围绕这条链组织共同能力，并把其它已定能力的依赖一起考虑。

禁止先按文件类型搭一个空壳目录，再逐功能复制网络、配置和错误逻辑。禁止为了维持现行架构说明而把新需求收缩成补丁。当前结构妨碍目标时，直接重画责任、数据形状和调用关系。

## 找出真正的责任

同一规则在多个入口重复，给它一个业务所有者。一个实体有多个内部可变副本，明确修改权和正式表示。不同外部协议需要不同转换，分别放在其边界。模块接口必须交代调用者实际需要的输入、结果、失败和生命周期，使复杂性留在负责模块中。

判断深模块使用 [责任与模块](references/ownership-and-depth.md)。转发层、通用 Manager 和多套 Adapter 同时出现时，追踪它们分别承担的责任；只维护旧形状的层次直接移除。避免按文件行数或抽象个数裁决结构。

## 识别共同基础能力

沿核心操作查配置、身份、网络、错误、数据、事务、缓存、后台任务、日志和资源释放。只建立该产品需要的能力，并从现有框架、标准库和成熟依赖中选择实现。共享能力须进入真实调用链，业务模块只传业务数据和处理领域结果。

遇到明确领域时，读取对应的专项技能，例如 [配置](../configuration/SKILL.md)、[存储与事务](../persistence-transactions/SKILL.md)、[异步生命周期](../async-lifecycle/SKILL.md)。无需先加载全部基础设施材料。

## 选择结构并完成一次贯通

按一起变化的业务责任决定边界和依赖方向。指定状态谁创建、谁修改、保存多久、谁消费；在真实外部边界处理协议转换。先用一个真实入口走通核心行为，暴露接口和生命周期问题，再把关联消费者迁到同一契约。

完整设计实例见 [从零贯通系统](references/greenfield-design.md)。已有系统替换见 [架构重判与演进](references/architecture-evolution.md)。用户只要求架构时写清可实施的组件、契约、流程和关键失败行为；已授权实现时继续完成迁移。

## 发现错误就重做负责的结构

出现多处重复判断、消费者自己拼装实体、需要新旧模型来回转换时，回到定义者修正。禁止再加一个统一包装隐藏多个所有者。必要时合并或删除自己刚创建的模块，保留用户要求的能力。

完成后应能从真实入口追踪到结果；同一规则、状态和基础机制有清楚的修改位置；新功能可沿现有契约接入。交付实际结构及决定性的理由，停止额外架构审计和证明活动。

新产品涉及多个入口共同修改有限资源时，读取[预约系统的完整结构](references/reservation-system.md)，从核心不变量组织领域、事务与用户路径。
