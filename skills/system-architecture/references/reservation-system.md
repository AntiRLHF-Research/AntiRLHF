# 预约系统：从用户动作建立完整结构

## 教学场景

设计一个设备预约产品。普通成员通过 Web 预约，管理员通过 CLI 代为预约；同一时段具有固定容量。用户要求能够创建、查看和取消预约，重启服务后数据仍然存在。当前部署为一个应用与一个数据库。

核心规则包括：同一预约具有稳定身份；容量不会被并发请求超卖；取消只能释放一次；成员只能操作被授权的预约。先围绕这些规则构建产品，通知、统计和复杂审批根据真实需求再接入。

## 决定修改权

预约服务承担创建与取消语义，确定有效身份、时段、数量及允许的状态变化。持久化实现负责将容量变化与预约记录放在同一事务中。Web 和 CLI 取得调用身份、转换输入、调用同一个服务，并把结果映射成各自界面。

```text
Web / CLI
    → 预约操作（身份、时段、数量、请求身份）
    → 预约领域判断
    → 数据库事务：容量变更 + 预约记录
    → 领域结果
    → 页面状态 / 命令输出
```

事务所有者必须有能力覆盖完整写入。把库存扣减和预约保存分给两个会自行提交的仓库方法，会使调用方失去原子性。选择应用层开启事务，底层共享该事务；或让一个存储操作完整提供预约写入。按项目已有机制选定一处。

## 用接口表达外部行为

以下接口是业务契约示意：

```typescript
type CreateReservation = {
  slotId: string;
  quantity: number;
  requestId: string;
};

type CreateResult =
  | { kind: "created"; reservationId: string }
  | { kind: "replayed"; reservationId: string }
  | { kind: "capacity-exceeded"; available: number }
  | { kind: "request-conflict" }
  | { kind: "forbidden" };
```

调用身份由认证边界取得后单独传给服务。`requestId` 用于重复提交时找到原结果；同一身份和请求号携带不同内容时返回冲突。内部可以使用项目既有异常体系表达相同结果，保持所有入口一致，避免同时维护字符串、布尔值和几套错误枚举。

服务实例在应用组合位置创建。数据库连接池、配置和日志接口由相应基础设施承担；业务模块使用已准备的能力。禁止每个入口重新读取配置、建立连接和决定重试。

## 首条路径就包含持久化

先完成创建预约、读取预约、重启后读取。随后接通 CLI 至同一领域操作，再完成取消。创建成功前事务必须提交；取消操作利用条件更新或项目既有并发机制确保只释放一次。

通知若属于本次范围，区分“预约已完成”与“通知待发送”。要求事务提交后可靠发送时，使用项目既有事务消息机制或成熟任务方案；单机演示不需要先建立分布式事件平台。

## 根据真实变化调整结构

增加候补队列时，候补和正式预约的身份、状态与容量关系需要重新判断。候补记录通常不占用正式容量；转正必须与占用容量共同完成。先更新这个领域操作，再迁移 Web、CLI 和后台处理。不要让三个入口分别写“候补转正”的条件分支。

管理员可以更改容量时，决定低于已有预约数量的操作如何处理。该决定影响领域契约，应在当前需求中说明。文件曾经叫 `BookingManager`，并不替它决定这些业务语义。

## 可以使用的组织形态

小项目可以让一个预约模块包含领域操作和事务实现，外部入口分别放在对应目录。业务增长后再拆开一起变化的职责。不要为每个名词创建接口、工厂、适配器和空实现。

完成状态是 Web 与 CLI 共用同一规则、并发与取消行为符合契约、重启恢复正常。实际事务示例见[存储与事务中的容量写入](../../persistence-transactions/references/atomic-reservation.md)。该例只展开事务机制；完整产品还需要上述身份、请求重复与入口责任。
