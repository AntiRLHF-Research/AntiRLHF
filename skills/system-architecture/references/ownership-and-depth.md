# 责任、状态和深模块

## 用变化定位责任

观察一次业务规则修改应影响哪里。例如修改发布权限时，若 CLI、API 和定时任务各改一次策略，授权责任已经分散。把权限判断和它依赖的数据放到发布服务，入口负责身份与协议。三个入口通过该服务执行，清理旧策略代码。

模块深度来自调用者获得的能力。一个 `publish(record, actor)` 操作可以拥有验证、事务和结果语义；若调用方还要手动同步三份状态、决定回滚和逐层转换，接口把复杂性漏回了消费者。先改善契约，再决定内部拆多少函数。

## 三种相似现象采用不同处理

同一业务规则重复：集中到同一个领域所有者，并迁移所有入口。不同协议碰巧有相似代码：保留各自协议职责，真正相同的基础算法由成熟库承担。同一实体在内部被改造成多种模型：选定正式表示，统一身份、状态和生命周期，消费者直接使用契约，外部序列化在边界完成。

把互不相关的规则堆进万能调度器会使每次改动都碰到中心模块。按变化原因拆开职责，让共享机制仅处理真正共享的事情。禁止为“统一”强迫所有传输、业务和持久化使用相同字段集合。

## 接口包含调用顺序和失败语义

接口描述应回答：是否修改状态、结果何时生效、并发冲突怎样返回、谁负责重试、取消后是否仍会产生效果。消费者无需重新猜测这些规则。

以导入服务为例，入口传递规范化输入及操作者，服务拥有去重、权限和提交事务。存储适配器负责数据库操作，UI 把已提交结果呈现给用户。无需把业务层变成理解所有数据库异常和 HTTP 状态码的万能适配层。

## 抽象的实际收益

保留能够封装真实变化、统一领域语义或明显减少重复工作的抽象。删除只改名、转发和维持旧测试的层。项目规模很小时，多个职责紧密一致的操作可以在一个模块内；新增职责使变化分离时再拆分。

禁止以“暂时只有一个消费者”否决已经确定的系统责任，也禁止根据想象中的几十个未来提供方制造插件注册体系。依据已定产品能力和真实变化选择结构。
