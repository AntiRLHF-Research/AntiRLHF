# 重新判断和替换已有架构

## 先识别任务是否改变了责任

用户要求整合多个写入入口、删除旧模型或扩大能力时，读取真实依赖关系，再判断原分工。现行规格记录了旧设计，修改规格应与新契约同步进行。禁止把“已有文档这样写”当作保留旧架构的决定性理由。

## 教学情境：离线配置与在线编辑

旧系统由 CLI 写文件、服务写数据库、页面修改内存副本。三个位置都认为自己拥有有效配置。简单增加 Bridge 会留下写入竞争。

选出有效配置的所有者。在线编辑经服务验证和提交；离线编辑确属产品能力时，将文件作为服务启动时读取的输入来源，定义加载失败和优先级。不要为了形式统一要求服务关闭时 CLI 仍必须连接服务。

迁移实际写入路径，清理旧字段转换、重复校验及其专属测试。读取者使用有效状态，不自行从文件和缓存重新拼装。重启后观察实际值，解决残留的双写。

## 改动规模与总负担

当多处修补来自同一个错误所有者，成组修改该责任及消费者。局部算法错误且所有者清楚，就在局部修正。用户要求缩减复杂度时，检查替代实现所需的测试、脚本和配置是否把旧负担搬回来了；回到新所有者继续简化。

## 并行工作中的架构决定

共享模型和状态修改由一个责任负责人统筹。先提供稳定的业务契约，再将独立消费者分给子任务。发现契约不合适时更新实际定义并通知消费者；禁止各自新建转换层以维持已经过期的任务说明。

## 与专项方法衔接

进入实体状态和不变量设计时读 [领域建模](../../domain-modeling/SKILL.md)。已决定替换而需要完整迁移时读 [结构替换](../../structural-refactoring/SKILL.md)。在当前责任层完成设计和实施，禁止让技能调用变成审批接力。
