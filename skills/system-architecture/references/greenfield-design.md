# 教学情境：从零建立文档导入产品

## 产品要求

用户通过命令行和 Web 上传资料，系统提取内容、保存处理状态并提供查询。首次交付是一个单机开发产品，用户要求调用真实模型完成摘要。部署需要在重启后保留任务与结果。

## 错误轨迹

分别为命令行和 Web 编写上传、解析、请求模型和保存逻辑。遇到状态不一致，再增加文件监听器、同步器和不同版本的任务对象。每个小函数都有测试，两个入口在一起却重复创建任务，重启后又丢失正在处理的工作。

## 目标责任

让导入服务拥有资料身份、状态迁移和去重规则。解析器承担文件内容提取，模型客户端承担协议访问和统一错误，存储拥有事务持久化，后台执行器负责调度、取消和关闭。CLI 与 Web 只将输入交给导入服务，并读取服务定义的任务视图。

需要的核心路径是：接收资料 → 创建任务 → 持久化身份与初始状态 → 执行解析和摘要 → 保存结果或失败原因 → 使用者查询。先决定任务状态和重启语义，再接队列或直接执行机制。

## 从成熟实现中选择

已有 Web 框架负责路由和生命周期；数据库驱动或 ORM 负责连接与事务；模型提供方的成熟 SDK 负责协议。文件解析采用格式对应的成熟库。只在项目中实现资料去重、领域状态和用户操作规则。禁止为所有通用机制重新编写插件框架。

单机任务较少且允许失败后人工重试时，持久任务表与受控工作进程可以满足需求。需要独立工作者、多实例分发和成熟重试机制时，选用现有队列系统。决定来自实际产品要求。

## 连续实施

先让一个真实入口创建任务并保存；让同一任务经过真实解析和模型调用完成；重启后从存储读回结果。随后接入另一入口并复用相同契约。把失败、取消和空结果反馈到使用者实际看到的位置。

配置在应用组合根加载，客户端和连接池在那里创建并释放。任务状态不由 UI、路由和后台工作者各自定义。发现输入形状不适用时直接修改领域对象和调用方，开发中无外部消费者的旧形状随迁移删除。

## 设计交付

交代上述责任、公开操作、任务状态、事务边界、资源归属和重启行为。代码目录依据这些责任组织。实现期间出现的旧猜测从现行规格中移除；历史讨论有用途时留在原讨论位置。
