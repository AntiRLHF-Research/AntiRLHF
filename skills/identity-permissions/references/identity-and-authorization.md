# 从可信身份到业务授权

## 让主体身份具有清楚来源

使用框架或身份服务已经验证的会话、令牌和账户信息。令牌处理采用相应库的签名、时效、发行方与目标校验能力。把外部声明转换为项目实际使用的主体，不在多个模块各自拆 Token 并创造不同角色表示。

## 规则属于操作与资源

授权需要知道谁对哪个资源做哪种操作。列表查询、单项读取和批量更新都要遵守相同的领域策略，避免只在一个 API 端点检查，另一个入口直接访问存储。前端按钮状态帮助使用者理解权限，实际执行仍由服务端或资源所有者决定。

## 教学情境：批量导出

单项读取按租户过滤，批量导出直接查询全部记录。修复共同查询与授权边界，让导出使用当前主体允许的数据范围。不要仅隐藏页面按钮，或者新建第二套导出角色体系。

## 共享规则与协议责任

会话 cookie、跨站请求保护和 HTTP 身份提取属于 Web 边界；资源修改条件属于业务。内部调用使用明确主体和正式授权操作，避免将 HTTP 细节灌进所有模块。真实不同的管理操作可以有不同策略，按语义定义。

## 错误与信息暴露

失败结果服务使用者下一步：重新登录、申请权限或选择有权资源。资源存在性是否公开按当前产品要求处理。日志保留排错需要的主体和动作标识，秘密内容留在秘密管理中。

技术参考：[OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)。采用具体认证库时核对其正式集成文档。
