# 从请求到后台作业的观测

## 教学场景

用户点击导入，接口立即返回作业 ID。后台下载、解析并保存数据。失败时 HTTP 层显示成功，日志中只有几段无关联的异常堆栈，用户看不到失败位置。

首先区分接收成功与业务完成。入口记录作业已接收，后台所有者更新作业最终状态，界面依据作业状态呈现结果。日志帮助追踪这个已经明确的数据生命周期。

## 关联信息只定义一次

请求拥有 `request_id`，持久作业拥有 `job_id`。跨进程任务消息携带作业身份及必要的追踪上下文；后台消费者创建自己的执行范围，并把相关身份附加到现有日志或 tracing 组件。

Python 项目可采用现有结构化日志库，或标准 logging 的 Adapter、Filter 与 contextvars；各自用途见 [Logging Cookbook](https://docs.python.org/3.13/howto/logging-cookbook.html)。在任务作用域结束时恢复上下文，避免下一项任务继承前一项身份。使用异步日志队列时，在生产日志记录的位置附加关联字段，不让消费线程猜测原请求上下文。

日志初始化、输出格式、脱敏和采样在应用组合位置集中配置。业务模块使用命名 logger，不重复添加 handler。已有 OpenTelemetry 接入时复用其上下文传播，禁止再造一套并行 trace ID 系统。

## 选择真正能解释故障的事件

以作业生命周期记录：接收、开始、成功、失败或取消。耗时、输入数量和成功处理数量在相应事件上记录。关键外部调用保留提供方错误码及操作身份，凭据、用户正文和完整个人资料按真实隐私要求排除。

同一失败由实际负责操作的层记录一次带原因的错误，外层负责状态和用户提示。每经过一个函数就打印相同堆栈会淹没真正的失败位置。需要区分不同阶段时使用事件名称或阶段字段，而非制造一套日志等级。

度量用于回答稳定的运行问题，例如失败率和处理时长。作业 ID 适合日志和追踪关联，不作为每个作业独立的指标标签。维度来自实际分析需求，不能把全部字段写进标签。

## 修复一次卡住的作业

真实症状是任务停在下载后。先通过作业 ID 找到最后一条事件，再沿下载响应关闭、解析开始与状态提交追踪。若缺失信息阻止判断，在该边界添加短期诊断。原因确认后修复负责的生命周期或状态变化，移除已经无用的临时输出。

观察原操作完成，界面读取正确状态，日志可以由作业 ID 连到最终结果。普通开发无需因此引入集中观测平台、全仓审计报告或永久的高频轮询探针。
