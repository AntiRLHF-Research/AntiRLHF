# 依赖选型与采用

## 在实现通用机制前选择承担者

读取项目已安装依赖、运行时和真实使用方式，再查对应的标准库、框架能力及成熟第三方实现。需要新能力就主动搜索；现有依赖不合适就允许替换。禁止因为保持依赖数量低、避免改动清单或展示编码能力而自己重写通用设施。

明确项目拥有的业务语义，例如内容分类、订单状态或权限策略。解析器、传输客户端、数据库驱动、国际化、加密和任务调度等机制优先交给合适实现。采用范围依据真正需要的能力。

## 比较决定性的条件

核对支持的运行平台、真实 API、数据模型、资源生命周期、失败行为、并发语义和集成成本。优先当前项目能够持续维护的稳定版本；新技术栈按其官方支持周期选择。不要把下载量、依赖个数和流行标签直接当成最终答案。

选择过程见 [选型到集成](references/selection-and-integration.md)。当两个候选在核心契约上有差异，做一项能够区分它们的实际调用，随后决定。禁止为了选一个解析库搭建永久评测平台。

## 直接吸收有价值的实现

成熟库符合需求就调用其正式 API；适合摘编的开源模块可以直接吸收源码及相关说明，保留所需来源与许可。用户要求复用原文技能时，按完整操作单元摘取，保留有效原句，仅改冲突条款，中文对应原有强度。

不要先读懂成熟方法，再按记忆重新造一份更薄弱的实现。也不要为了统一所有库给每个 API 套一层转发类。项目确实需要隔离不同提供方语义时，在真实边界定义薄而完整的适配契约。

## 迁移后让旧实现退场

把选定能力接入用户路径，迁移当前消费者、配置和资源释放位置。删除已被依赖接管的通用代码、专属测试和临时脚本。用项目自己的集成行为检查接线，不复制上游对解析、编码和传输内部细节的测试。

已有库版本不合适时，修改依赖和实际调用，避免长期维持一个“兼容所有版本”的自制分支。真正的公开支持范围写在现行契约中。

## 许可与来源按实际使用处理

按实际采用与分发方式保留需要的版权、许可及 NOTICE。在共同分发根维护同一来源的声明，覆盖实际带出的材料；源码原有且要求保留的版权头继续保留。禁止在每个技能、参考章节和调用处重复添加许可说明，禁止反复核验已经明确的同一来源。缺失的许可信息只在影响采用时处理。

源码与文档摘编方法见 [原文复用与局部修改](references/source-adoption.md)。交付具体选择和集成结果，停止继续比较已经失去决策价值的候选。

接入通用格式解析时，读取[以标准库替换 CSV 手写解析](references/csv-import-adoption.md)，保留领域校验和错误呈现，删除旧解析与配套机制。
