# 项目事实、持续要求与临时纠正

## 教学场景

用户让 Agent 初始化项目说明。仓库已经有构建命令、配置入口和领域规则，Agent 却写入自己熟悉的“每次修改先写失败测试、每步审查、每次完成提交证明”。随后同一模型和后续模型都会把这些偏好当成项目要求。

先读真实源码、现行命令和有效用户决定。初始化指令应帮助下一位开发者理解并使用这个项目，不能把模型熟悉的方法升级为新的制度。

## 选择能改变实际操作的信息

值得记录的内容包括：正式状态由哪个模块修改、生成文件从哪里产生、当前启动命令、真实数据存放位置、支持平台和用户明确的长期约定。例如以下教学素材：

```text
目录记录的写入由 catalog/service.py 负责，HTTP 与 CLI 调用同一操作。
修改 schema/ 下的定义后，使用项目已有生成命令更新生成客户端。
开发数据路径来自 APP_DATA_DIR；不要把本机绝对路径写入源码。
```

路径和命令必须对应当前实际仓库。模板中的占位项目事实不能直接复制。通用工程知识留给已安装的专项 Skill，项目指令只写会改变这个项目工作方式的事实和要求。

## 临时纠正回到原处

用户指出一个文案多余，修改该文案；指出某处接口应该直接替换，迁移对应契约和消费者。只有该反馈明确建立了跨任务长期要求，才更新负责的指令文件。

纠正过程、道歉文字和旧错误的否定说明不进入当前规格。历史记录需要保存时放在原有发布或研究位置。禁止把每次反馈变成额外禁词、反向测试和永久检查脚本。

## 拆分本地知识而不增加通用入口层

常驻指令承载具体的共同取向。专业 Skill 描述任务、反复错误、正确方法及完整操作关系。References 承担深入技术和案例。让配置、领域建模、作者写作等任务直接找到相应 Skill；用户无需先进入统一“计划/执行”路由才能拿到专业方法。

一项规则明确由一个位置维护，其他材料引用该位置。针对高频惯性，在关键动作旁保留简短而有针对性的重复提醒，防止被长文稀释。完整技术细节继续留在对应参考，避免复制出相互矛盾的版本。

## 吸收上游方法时沿实际引用处理

摘入成熟方法的有效原文和代码，给出完整中文译文。对强制测试、普遍审批和逐任务审查的条文直接修改；检查被采用段落引用的其他 Skill，防止通过依赖再次加载冲突流程。

有效实例和方法保留足够深度，禁止为了省字将其重新压缩成抽象口号。来源与许可由分发材料维护，运行正文聚焦执行者要做的事。正常使用从本地读取，不要求访问治理仓库或先完成来源核验。

## 维护现行知识

新接口替换旧接口时同步更新相关说明，删除已经失效的约束及旧专属支撑。阅读当前内容就应能开展工作。不要让开发者先穿过一份不断增长的“禁止重犯历史错误”列表。
