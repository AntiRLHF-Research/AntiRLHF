# 把反馈合并到责任所有者

## 教学场景

评审给出三条意见：CLI 的默认路径不对；Web 保存后后台仍读取旧路径；重启恢复值不同。第四条意见要求改变界面配色。当前用户授权修正配置行为，配色尚未选定。

采用[反馈处理方法](review-feedback-method.md)，完整理解意见后读取真实配置入口和消费者。前三条可能来自同一份配置的多个所有者，应一起调查。配色是独立问题，不能阻塞已明确的配置修复。

## 用事实决定修正方向

若检查发现 CLI、页面和 worker 各自解析环境变量，集中配置来源和有效状态，迁移这三个消费者。不要照评论顺序各改一处默认值。修复后的结果应是设置一致，来源有明确优先级，重启读取同一正式表示。

若评审误读了离线 CLI 的产品需求，说明 CLI 确实需要服务停止时编辑文件，并为启动加载设计同一验证契约。不能仅以“旧设计如此”拒绝反馈；真实能力才决定保留何种边界。

## 保持授权内的推进

有真实待决项时说明它影响的部分。独立且明确的修复直接完成。外部公开回复、推送或发布按用户授权处理，不把读取评审意见自动扩成对外操作。

当反馈推翻了自己的判断，直接改对应实现、说明和测试。回复只交代实际变化及需要对方决定的事项。禁止再写长篇认错、模型内部动机解释和永久承诺。

## 反馈怎样变成长期知识

本次修复确立的配置所有者和输入优先级可以更新到原有开发文档。某条评论的具体措辞、误会经过和临时排错步骤留在评审线程。禁止把“一次默认值写错”扩展成所有提交都要运行的配置证据审计。

如果用户要求分析自己的改稿，依据已有原文和改稿解释立场、信息取舍、语气和结构变化；有 Diff 就利用，没有 Diff 也直接比较现有材料。这个任务的成果是分析，未经要求不要另交修订稿。

## 完成时回到真实要求

相关入口已经读取统一设置，原故障路径得到修复，当前说明同步更新后结束。独立未决配色只保留其实际问题，避免为每条意见分别生成测试、提交、复核和批准状态。
