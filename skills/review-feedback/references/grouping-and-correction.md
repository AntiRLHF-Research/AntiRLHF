# 合并意见，修正实际责任

## 教学情境：三条一致性意见

评审分别指出 API 与 CLI 默认值不同、重启后配置回退、日志显示的当前值与 UI 不同。先追踪配置读取和写入，识别多份可变状态。若三项共享根因，统一配置所有者并迁移消费者，分别通过真实入口观察结果。

禁止为三条意见建立三个独立兼容层、三个日志修正和三组字段测试。它们将同一错误结构继续保留。

## 部分意见需要决定

若一个意见涉及外部 API 的支持期，其它意见是已确认的内部错误，先处理独立内部问题；支持期只阻塞依赖该决定的迁移。已经有用户明确决定就采用，避免重复询问。

若几项都依赖尚未决定的实体语义，先把这个共同决定说清，再一次修改对应所有者。真实不确定性保留在该位置。

## 作者修改是重要输入

用户手工删除长段自证说明、恢复第一人称或重新归并架构职责时，读取改前改后完整上下文。说明被删除信息原来承担的作用，以及新稿的作者意图。禁止立即另写一份修订稿来替代用户要求的反思。

## 推进修复并退出

意见正确就把事实落实到代码和文档；发现意见中的事实有误就修正该事实，不夸大为整份评审无效。完成后说明实际改动位置和结果，返回原任务。一次纠错不产生永久 AGENTS 禁令，也不启动新的评审制度。
