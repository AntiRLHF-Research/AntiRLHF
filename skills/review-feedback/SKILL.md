# 评审意见处理

## 先理解意见要求的行为

完整读反馈和对应上下文。确定用户要求的是判断、解释还是实施修正。不要先表态全部接受，也不要因为意见不符合旧设计就机械反对。以当前目标、实际代码和真实外部契约作判断。

采用 [反馈处理方法](references/review-feedback-method.md)：读取、理解、核对、判断，简要表达技术结论，按真实所有者合并修改。

## 查会改变结论的事实

读取指出的位置、实际调用方与相关契约，确认触发条件和影响。已知信息足够就判断。反馈含多个独立事项时先完成明确部分；确实互相依赖的未决语义才需要一起澄清。禁止一项无关疑问冻结全部工作。

旧接口和旧测试的存在只是现状。实际外部消费者、持久数据及明确支持承诺才决定过渡要求。用户提出架构重判时，旧文档同样进入修改范围。

## 按根因和所有者组织修复

多条意见来自同一状态或规则错误，合并为一次结构修正。迁移受影响消费者、配置、测试和现行说明，删除已被替换的机制。不同责任保持独立，不按评论顺序盲加局部补丁。

需要重新设计时使用 [结构替换](../structural-refactoring/SKILL.md)。检查用 [有效验证](../meaningful-verification/SKILL.md) 的相关方法选择，取消逐条意见必跑测试的通用要求。

## 用事实修正判断

原先反对的意见被证实正确，就直接修正结论和产物。禁止长篇道歉、解释模型内部动机或写未来承诺。用户要求分析修订时，读取已有版本或差异文件，说明改动对含义、结构和读者的影响；材料足够就完成分析。

无法成立的意见给出明确技术理由；有真实取舍由用户决定时，说明影响决定的条件。不要把鲜明结论弱化为谨慎姿态。

## 回到原讨论并完成

已授权的修复做完后简述实际结果，相关 GitHub 行内意见在原线程回复。用户未要求外部回复就只交付本地结果。没有新缺陷时结束，禁止请求另一轮全量审查证明自己已经听取意见。

反馈组合案例见 [根因合并与纠错](references/grouping-and-correction.md)。

收到多条相关评论时，读取[把反馈合并到责任所有者](references/resolve-feedback-at-owner.md)，区分事实错误、当前需求和独立待决事项，再完成修正。
