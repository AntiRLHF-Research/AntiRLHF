# 共享契约与独立子任务

## 教学场景

用户要求统一错误模型，并把 Web、CLI 与后台任务一起迁移。三个 Agent 同时开工，各自创建错误枚举，再互相转换；主 Agent 最后增加 Bridge 拼接结果。任务完成了许多局部修改，错误语义仍然分散。

先由一个明确所有者设计并实现正式错误模型，交代领域类型、保留的原因链及边界转换。模型尚未确定时，可以并行调查不同入口的现状，但修改共享模型由同一个所有者统筹。

## 契约稳定后再分发消费者

独立子任务使用已经存在的契约及实际代码位置。给 CLI 的简报可以包含：迁移 CLI 输出和退出状态、调用正式领域操作、保留现有用户能力、清除本入口私有字符串判断。给 Web 的任务说明对应错误如何映射到用户动作。后台任务明确哪些错误会重试、哪些结束。

不要用“只让测试通过”定义任务，也不要禁止必要的生产修改。修改范围围绕真实责任划分；遇到共享契约缺口，回到统一所有者调整，再通知相关消费者。禁止子任务私自增加兼容枚举绕过问题。

## 一份可直接执行的简报

```text
目标：CLI 使用正式导出操作，用户能区分输入错误、无权限与远端失败。
已定契约：读取 domain/export.py 和 errors.py；错误语义由该模块拥有。
责任：修改 CLI 参数转换、调用与退出状态；迁移相关有价值用例。
共同约束：保留用户已有无关改动；不得另建领域错误版本。
发现契约缺口：给出缺失行为及实际调用位置，交由共享所有者修改。
交付：可运行 CLI 路径、已修改位置、仍有的具体阻塞。
```

真实路径按当前仓库填写。简报携带必要上下文、有效决定和授权；无关对话历史无需复制。源方法参见[独立任务组织](independent-task-method.md)。

## 合入实际系统

检查每个结果怎样调用共享所有者，将成果合入当前主线。实际冲突先辨别是否来自错误分工：两个任务修改同一个领域模型，通常应由一个所有者完成；两个独立入口只是同时修改导出列表，可以集中处理该接入点。

运行受到组合影响的真实操作。一个局部测试通过后仍要接通未迁移入口。不要自动为每个子任务再启动实现审查、规格审查和最终审查的多层链。

## 并行的结束条件

每个任务完成自己负责的能力和相关反馈后返回。调查已回答的问题不重复展开；共享结构变化只通知真正受影响的消费者。最后交付同一个连贯系统，撤掉临时协调文件和已经失效的旁路实现。
