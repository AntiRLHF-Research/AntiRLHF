# 按实际读者组织同一事实

## 教学场景

产品新增“保存筛选条件”。用户能给筛选命名，下次打开页面继续使用；开发实现将筛选保存在用户配置中，并提供版本冲突处理。需要更新使用指南、开发文档和作者发布文章。

三份作品共享同一实际能力，读者要完成的事情不同。先读取各自原文及相关实现，把信息放到读者会使用的位置。

## 使用指南交付操作

可采用以下正文：

> 在列表中设置筛选条件，点击“保存筛选”，输入名称。下次从“我的筛选”选择它即可恢复。修改已保存的筛选后，点击“更新筛选”。

如果当前产品没有“更新筛选”按钮，就按真实实现写操作并指出功能缺口。不要为了让指南完整编造可用能力。保存失败、名称重复或权限限制需要改变用户动作时，放在对应操作附近。

该段不需要介绍配置 Schema、冲突检测算法、开发过程中通过的测试和使用的组件库。

## 开发文档交付当前契约

开发文档说明筛选身份、所有者、字段结构、保存与读取入口、权限和冲突行为。写清哪些字段是领域规则，哪些只是展示状态，如何迁移真实旧数据。内容来自当前实现及有效决定。

例如：筛选服务拥有名称唯一性和修改版本；页面提交当前版本，存储条件更新；版本冲突返回正式领域错误。调用方通过该契约更新，避免自行读配置文件后覆盖保存。

内部模型已经替换时，在原有说明中直接写新契约，移除旧入口。真实发布历史放在发布记录；当前 API 文档不保留长篇旧设计悼词。

## 作者文章保留发言者

发布文章可以讲作者为何需要这个功能、在实际使用中怎样改变工作，以及原有表达中的幽默或克制。先读作者此前文章，沿用其人称、节奏、立场和读者关系。

已有真实修订对照见[研究文稿案例](../../direct-writing/references/cases/charter/README.md)。作者把第三方“维护者提出”改成直接承担观点的表达，纠正的是发言位置。不要把这种改动再写成“所有文档必须第一人称”的规定。

作者要求局部补充时，只改相关事实和衔接。翻译时保留判断强度和内容用途，避免加入译者的免责、来源审计和文档性质声明。

## 写作完成的实际判断

使用指南能让读者完成当前操作；开发文档让贡献者调用正确接口；作者文章保留作者想表达的意思与风格。三者都可以有真实条件，但条件服务各自的读者行动。

修改事实导致多份当前说明失效时，同步更新其实际引用。原有文本没有错误的部分保持原样。没有真实持续用途的编辑记录、临时提醒和过程自证不进入正式作品。
