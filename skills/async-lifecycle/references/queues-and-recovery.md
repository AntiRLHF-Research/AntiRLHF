# 队列、幂等和重启恢复

## 用真实需求决定是否持久化队列

请求内短工作可以直接等待。应用内后台工作需要受控任务生命周期。进程重启后仍需继续、多个工作者共享任务或需要成熟投递语义时，采用技术栈已有队列与调度组件。禁止一开始就制造跨提供方消息平台。

## 任务身份与业务幂等

队列投递语义需要与实际业务协调。任务重投可能再次执行，领域所有者用业务身份、唯一约束或已有幂等机制避免重复副作用。队列消息 ID、一次尝试 ID 和业务操作 ID 分别承担各自职责。

确认消息应在该次工作达到对应完成点后发生。错误分类决定重试、终止或人工处理；取消和业务拒绝通常有独立语义，禁止所有异常走同一重试分支。

## 重启恢复

任务状态持久化归正式所有者。进程重启后读取真实进行中工作，按产品决定重排、恢复或标记失败。需要租约或超时回收时优先用现有队列提供的能力，不再给每个工作者加一个私有恢复定时器。

## 教学情境：文档处理任务

上传创建业务任务，工作者读取并调用解析与模型服务，结果持久化后确认。外部调用超时且结果未知时，按提供方查询或幂等能力处理。用户取消后不再新开模型请求；已有响应按明确状态落地。

失败原因、可重试性和重试预算写在任务契约中。UI 展示正在处理、完成或能采取行动的失败状态，禁止显示内部所有投递步骤和验证经历。

## 采用现有能力

查看当前项目的队列、调度库和数据库任务机制，按可靠性、部署条件与操作规模选用。使用其正式的确认、重试和关闭方法，再验证项目实际接线。上游队列内部调度测试无需复制。
