# 缓存身份、失效和并发

## 从读取语义选择机制

用户要求保存后立即读到新值，就把写后读路径设计清楚：绕过旧缓存、更新相应缓存或读取正式状态。允许短暂滞后时，明确产品可接受的刷新语义。不要用一个全局 TTL 代替所有业务决定。

缓存键包含真正决定结果的身份和查询条件。租户、权限范围或版本影响结果时，将它们纳入键或相应隔离边界。禁止跨用户复用含私人结果的缓存。

## 失效竞态

一次旧读取在更新提交后才填入缓存，可能使“提交后删除缓存”再次被旧值覆盖。根据实际一致性需求选用版本检查、原子更新、短期旁路或成熟库提供的协调机制。先定位是否存在这种竞态，再引入相应处理。

## 缓存失败

缓存可重建时，失败路径可以读取正式存储，并受实际并发和服务容量约束。不要无限绕过造成下游雪崩，也不要为每个功能重复写 fallback。由共同缓存边界定义读取失败和回填规则。

## 教学情境：记录标题更新

更新服务提交标题后，页面仍显示旧值。先追踪页面是否使用本地副本，API 是否读取缓存，缓存是否订阅实际提交。修正对应所有者后执行 update → read。不要同时在 UI、API 和后台加三个强制刷新定时器。

## 清理重复机制

统一责任后删除旧缓存镜像、私有过期策略和不再使用的刷新任务。性能尚无实际问题时保持直接读取，禁止为证明自己考虑周全引入多级缓存。
