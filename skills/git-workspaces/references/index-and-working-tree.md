# 提交、暂存区与工作区

## 教学场景

用户已经暂存一批修改，要求先提交这些内容，然后修正评审问题并暂存，最后扩展内容但保留未暂存。这里三个位置承担不同审阅责任：HEAD 保存用户选择，index 保存待提交修正，working tree 保存探索性扩展。

这项顺序来自明确用户要求。普通任务按实际授权采用所需 Git 操作，不额外制造分层流程。

## 先理解已有状态

```bash
git status --short
git diff --cached
git diff
```

查看暂存与未暂存差异，确认哪些属于用户已有工作。存在未跟踪文件时按内容和任务判断其归属。禁止先 `git add -A` 把所有变化混进用户提交，也禁止用 reset/clean 清掉不认识的工作。

用户明确要求提交当前暂存内容时，直接提交当前 index。身份沿用项目或用户授权配置；缺失时仅为本次操作设置必要信息，不改全局配置。提交成功后再开始新的修正。

## 先暂存修正，再继续扩展

完成修正后，按实际路径或 hunk 暂存对应内容。修改包含文件更名时，同时处理删除与新增；技能目录改名还要迁移元数据、调用名和本地链接。

确认 index 包含完整修正后，继续编辑文件扩充内容，保持这些编辑未暂存。同一文件可以同时拥有暂存和未暂存差异。后来执行普通 `git add 文件` 会把该文件的新内容一起放进 index，必须避免破坏已要求的层次。

```bash
git diff --cached   # HEAD → index：待提交修正
git diff            # index → working tree：已跟踪文件的扩展
git status --short  # 同时查看新增的未跟踪文件
```

状态列左侧显示 index 的变化，右侧显示工作区变化。新增但未暂存的文件还不会出现在普通 `git diff`，应通过状态列表和文件内容审阅。不要为了让它们出现在 diff 中擅自暂存。

## 中途发现遗漏修正

如果已经开始扩展才发现必须修正的元数据错误，先识别这个改动属于哪一层。使用精确 hunk 或只针对相应 index 内容的补丁处理，保留扩展仍未暂存。内容复杂时暂停混合写入，读取两层差异后再编辑；不要粗暴重新暂存全包。

## 交付需要保留这些状态

交付供继续审阅的仓库时，归档包含 `.git`、index、工作区及未跟踪的新文件。解压后应可继续使用上述命令看到同样边界。远程 URL、凭据和用户配置按实际内容处理，禁止通过归档额外泄露凭据。

提交历史、暂存区和工作区已经承担审阅用途，无需再为每个文件制作独立 SHA 对齐表。用户要求普通发行包时，按[发布材料](../../release-integration/SKILL.md)组织实际分发内容。
