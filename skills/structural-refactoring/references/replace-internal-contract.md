# 批量发布：替换内部契约并完成所有消费者

## 教学场景

内容工具有 CLI 单项发布、Web 批量发布和定时发布。三处分别调用 `publish_raw`、`publish_v2` 与 `legacy_publish`。各自处理权限、发布时间和错误字符串，批量入口还忽略部分失败。用户授权统一发布能力，当前内部接口没有外部支持承诺。

## 定义真正要保留的结果

发布服务取得操作者、内容身份及发布请求，统一判断权限、内容状态和发布时间。单项操作返回明确领域结果；批量操作调用相同规则，并返回每个内容的结果。批量是否整体回滚来自产品约定，不能由旧方法的命名决定。

先选定正式实体与结果表示，让读取方得到一致的状态。仅新增 `UnifiedPublishBridge` 再调用三套旧方法，会保留全部冲突来源。直接改动拥有发布规则的实现。

## 迁移沿实际引用展开

从三个入口追踪到业务服务、数据库更新和通知，再检查 CLI 命令注册、后台调度表、依赖注入配置及打包入口。生成客户端存在时，修改其 Schema 或生成源后再生成。全仓文本搜索辅助查残留，动态消费者需要读实际注册机制。

在同一开发分支里创建新契约并迁移真实调用方。类型检查和调用路径中的失败用于定位未迁移消费者。不要为了让每个中间提交都保持旧测试原样通过，添加永久别名和第二套行为。

对于真实存储数据，根据已有记录迁移；无用户数据的实验文件可以随旧结构退出。读取数据迁移方案与[存储迁移](../../persistence-transactions/references/migration-and-recovery.md)配合使用。

## 测试场景与旧实现分开处理

旧测试里的“未授权用户无法发布”“延迟发布时间正确”“通知失败不回滚已成功发布”可能仍有产品价值，迁到新的正式操作。模拟私有 `legacy_publish` 调用次数、断言 V2 中间字典和验证 Bridge 对齐的测试随旧实现一起删除。

若新的调用链需要多份 Fixture 工厂、结果转换 DSL 和测试专属入口才能运行，继续检查新接口为何没有直接提供业务操作。简化目标覆盖刚新增的支撑代码。

## 结束时留下一个当前系统

删除旧函数、别名、注册项、配置键、专属 Mock、旧使用示例与现行文档中的过时操作。CLI、Web 和定时入口都调用同一个发布所有者。运行受影响的真实发布路径，处理实际集成错误，然后交付。

发布历史可以继续记录旧版本。当前指南直接描述新操作。代码注释解释现在的规则与必要原因，不保留一排关于已删除接口的警告。

## 遇到真实外部边界时调整迁移位置

如果发现确实仍有受支持客户端使用旧公开协议，就在公开入口完成协议转换，内部继续统一。把支持期、真实数据转换和部署顺序写在承担该义务的位置。其余仓库内部消费者按新契约迁移，不为想象中的客户端延续全部旧代码。
