# 按行为和独立故障安排验证

## 找到当前结果的失败方式

一个检查应观察项目真正负责的行为。解析业务输入时，保护领域字段映射和错误处理；CSV 库的引号解析留给库。存储操作时，保护提交、冲突和读取结果；数据库每个内部操作的正确性由成熟实现维护。

关键区别是失败位置：权限算法算错，和 API 完全没有调用权限算法，可以分别失败。算法测试与入口检查承担不同责任。十个 Helper 各断言一个默认字段，最后又在 Mock 上重复检查同一默认值，则需要合并到拥有该契约的位置。

## 选择观察方式

纯算法使用直接输入输出检查；状态机通过正式操作观察状态迁移；存储和协议集成使用真实驱动与受控资源；UI 通过用户操作看结果。已有检查足够时直接复用。不要为了统一形式把所有检查塞进新框架。

## 教学情境：批量导入

用户要求原子导入一批记录。应观察合法批次全部保存、非法记录的处理语义、重复记录策略以及失败后的数据库状态。检查某个私有函数有没有被调用三次，无法覆盖事务是否真的成立。

如果用户需要允许部分成功，业务契约随之改变：结果应列出成功与失败项，存储边界按这个语义组织。先决定产品行为，再写保护它的检查。禁止用已有测试预设的原子性反过来拒绝已经授权的需求改变。

## 真实使用路径

从入口执行创建、读取、修改或取消操作，看状态、外部效果和用户反馈。涉及重启就真的重启读取，涉及模型就完成授权内真实调用。单元测试通过后仍然接通未完成的消费者。

## 结果与下一项动作

失败指出需要修改的所有者；通过说明当前问题已解决。随后继续剩余能力，禁止因为得到了绿色信号就再增加一组浅层测试庆祝完成。有持续价值的回归进入正式行为测试；临时探针、探索性断言和复制样板用完删除，继续调查所需的本地材料保持在 Git 之外。
