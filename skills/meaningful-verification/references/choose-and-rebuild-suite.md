# 按独立失败重建验证

## 教学场景

项目把旧的文件与数据库双写配置系统替换成一个配置所有者。用户还要求减少维护负担。旧测试大量检查字段映射、私有 Helper 调用次数和模拟存储返回值；新的测试准备复制这些断言，再加一层通用 Fixture 框架。

先根据目标系统判断实际会失败的地方：输入是否被正确解释、更新是否由同一个所有者处理、保存失败后有效值是否一致、重启是否读取已保存值。由这些责任决定检查对象。

## 迁移用例时保留场景

| 旧用例保护的内容 | 新系统中的处理 |
| --- | --- |
| 合法配置缺少可选字段时采用默认值 | 转移到正式配置解析入口 |
| 私有 `V1Adapter.toLegacy()` 被调用一次 | 旧适配器退出后删除 |
| CLI 保存后重启能够读取 | 迁移到真实 CLI、持久化和启动链 |
| 页面和服务各自验证同一字段 | 规则测试集中到配置所有者，入口仅检查实际接线 |
| 保存失败时页面没有显示为已生效 | 保留这项用户可见失败行为 |

迁移通过的是场景和契约，旧断言的函数名、Mock 层次和 Fixture 工厂可以整组退出。不要为了让旧测试保持原样恢复一个已淘汰的生产导出口。

## 单元、集成和真实使用各承担具体问题

复杂解析、排序算法或策略组合可以在纯领域入口测试。数据库事务失败与重启恢复需要真实持久化路径。Web 控件是否提交了正确命令需要入口接线或实际使用观察。

有两个测试都提到同一字段时，检查它们是否能独立失败。领域校验正确、API 却完全绕过该校验，是两项独立问题。三层 Mock 都返回自己刚构造的同一个字段，只是在反复展示夹具。

使用替身隔离真实难以触发的外部故障时，让替身实现项目正式边界。禁止仅为创建替身给生产代码增加公开 setter、通用 ProviderRegistry 或第二套生命周期。已有成熟测试工具能表达的故障就直接采用。

## 观察结果决定下一项工作

解析检查通过而 CLI 仍写旧文件：下一项修改迁移 CLI。一次集成运行暴露保存失败后内存状态已更新：修配置事务或状态切换。错误定位到共享所有者时，成组修正受影响入口；不为每个入口各加补偿。

没有相关变化时停止重复运行同一完整套件。新的修改影响持久化、状态顺序或入口接线时，再选择能观察该变化的检查。用户要求的功能仍未接通，就继续实现该功能。

## 临时观察和长期回归分开

排错用的一次性打印、现场数据复制和试验脚本留在任务工作区或临时目录，用完删除。真实回归有独立保护价值时移入项目的正式测试位置，连同其必要输入维护。不要因为某个探索文件曾经帮过忙就把它变成永久测试资产。

结束时删除旧测试组及只为其存在的 Mock、脚本、配置和工作流入口。总代码、理解负担与用户能力一起检查；测试数量下降却新增大型场景 DSL 时，继续精简刚建立的结构。
