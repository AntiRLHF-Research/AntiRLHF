# 存储与事务

## 明确状态由谁决定

沿实际操作查实体身份、读取者、写入者、持久化位置和恢复路径。领域所有者决定业务变化，存储机制承担数据读写与事务。禁止路由、任务和界面分别维护一套可写状态，随后用同步器弥补分歧。

选择项目已有数据库驱动、ORM 和迁移工具，直接采用其事务、约束和连接管理。无需为所有表制造通用 Repository 框架。实际领域契约需要隔离存储时，提供完成业务操作所需的接口。

## 把一次业务变化放进正确事务

确定哪些状态必须一起提交，哪些外部调用会耗时或产生不可回滚效果。由工作单元所有者统一事务，禁止底层 Helper 自行提交，导致调用者以为整体原子而实际分段生效。

使用 [事务与并发](references/transactions-and-concurrency.md) 选择约束、条件更新或锁。失败时保留真实事务语义，不靠重复写入和多级 fallback 掩盖部分成功。

## 区分真实存量和内部历史

需要保留的用户数据按正式迁移处理；内部接口和可重建缓存直接收敛到当前形状。字段、索引或数据格式变化，修改权威定义及实际读写者。禁止为开发历史保留多套 writer、reader 和永久版本转换。

迁移与重启方法见 [迁移和恢复](references/migration-and-recovery.md)。实际支持的公共协议在边界处理，内部统一模型继续使用。

## 接通缓存与外部效果

数据库提交后的缓存失效由状态所有者负责。外部通知或工作调度需要可靠发送时，使用已有事务消息或 outbox 能力；只有实际可靠性要求成立时引入相应持久机制。

缓存和事件细节读取 [缓存与事件](../cache-events/SKILL.md)。不要每个模块独立发消息、再各自补一个补偿定时器。

## 观察真实行为并结束

通过真实入口执行写入、读取和要求中的重启。保护独立失败：约束冲突、部分写入、并发覆盖和迁移后的读取。成熟数据库内部行为由上游承担，不重复实现和测试事务引擎。

完成正式写入路径、真实数据过渡及旧实现退出，更新当前开发说明。交付用户能力，不追加永久存储审计平台。

容量扣减和业务记录必须一起保存时，读取[原子预约与一次取消](references/atomic-reservation.md)，用实际事务与条件更新实现并发规则。
