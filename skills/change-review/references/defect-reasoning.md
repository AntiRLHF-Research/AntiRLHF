# 从真实变化推导缺陷

## 审查责任链

变更一个共享模型时，读取定义与消费者怎样解释字段。变更缓存时，读取写入、提交、失效和重建。变更权限时，读取身份来源、策略和实际入口调用。表面 diff 很小也可能影响完整链路，范围由真实关系决定。

## 教学情境：字段测试全绿，配置仍然失效

新端点把配置写进数据库，CLI 仍然修改文件，启动继续读文件。审查发现的核心问题是有效配置有两个写入来源。将其作为一项结构缺陷，描述 API 保存后重启读回旧值的条件，并提出统一修改和加载契约。

不要分别报告“缺少集成测试”“缺少日志”“缺少文档”“需增加监控”四项外围问题来掩盖实际责任错误。直接修正所有者及消费者，必要检查跟随真实行为。

## 证据与操作尺度

编译错误可由编译器直接定位；并发缺陷需要理解状态与时序；数据迁移要看实际存量和支持范围。选择能回答当前问题的材料。禁止固定要求每项发现都附截图、SHA、复现脚本和风险矩阵。

已有测试失败的原因可能是产品错误、环境问题或已淘汰契约。按照真实契约判断后再给结论，不先要求实现迎合所有旧断言。

## 报告写成可行动的文字

使用有语义的标题，例如“重启读取仍走旧配置来源”。说明受影响入口、触发操作和具体改动位置。采用项目既有严重程度约定，避免自创编号和评分系统。已确认的结论保持力度，真正缺少的事实紧挨相应问题说明。

审查结束点是用户的问题已经得到回答。新的等价风格意见不触发新一轮循环。
