# 沿实际行为发现缺陷

## 教学场景

PR 声称“取消后台生成”。修改新增了取消按钮，把数据库状态改为 cancelled，并让单测断言状态字段。后台 worker 仍在运行，结束时覆盖状态为 completed，还继续保存结果。

先读取用户要求的取消行为、相关差异与实际 worker。追踪取消入口到任务执行，再到最终持久化及 UI 读取。无需先审查仓库每一条编码风格。

## 从可触发条件组织发现

一项可行动的发现应该包含：生成任务仍运行时点击取消；入口只改状态，worker 没有取得取消信号；worker 结束后无条件提交完成；用户看到取消失败且计算仍继续。

负责位置是任务生命周期与终态提交。修复可以把取消信号传到运行任务，并让完成写入受当前状态或任务版本约束。具体实现由项目已有执行器决定。禁止只给取消按钮增加第二次状态写入。

这个发现即使涉及三个文件，也归为一个根因。不要把“按钮没有停止 worker”“状态后来变 completed”“日志仍然打印成功”分别列成三个独立大问题。

## 区分真正独立的遗漏

如果下载端点同时允许另一用户读取结果，那是单独的授权缺陷，追踪自己的入口与身份判断。若某个函数名不符合个人偏好，但行为和项目约定都成立，不将其升级为修改要求。

已有规范与产品方向冲突时，说明实际后果并重判规范。测试已经通过时仍要读相关真实调用链；测试失败时判断失败契约是否仍有效。没有当前义务的旧断言不应迫使恢复错误架构。

## 工具选择围绕疑点

需要确认取消时序，可以用现有任务执行路径和可控等待复现。需要确定动态注册是否仍引用旧 worker，就查注册来源。一次检查已经定位问题，就报告该发现或在授权内修复。不要追加全面性能基准、全依赖许可审计和大量理论安全问题。

## 交付与修复的边界

只读审查交付位置、触发条件、影响和修正方向。明确授权修复时，修改实际所有者并运行对应操作。没有实质问题时直接给出判断，任务结束。禁止为了让审查显得有用而继续制造小问题，或在修复完成后再自动派出一轮审查者。
