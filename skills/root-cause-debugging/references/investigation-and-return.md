# 调查、修复和返回主线

## 用观察区分原因

接口返回成功而重启后结果丢失，可能发生在未提交事务、写错存储位置或启动时加载旧来源。追踪写入与重启读取的路径。先查看实际提交点、配置和加载位置，再决定需要哪条日志。

一项诊断只回答一个活跃未知。观察能够区分持久化失败和缓存旧值，就用这条结果选择下一次修改。禁止先编写通用一致性审计器、全链路回滚机制和长期监控来代替定位。

## 处理间歇性问题

缩小触发条件，保留任务上下文和资源生命周期。使用现有工具的事件等待、同步原语、受控时钟或固定输入重现竞争。故障出现概率影响定位策略，选择有意义的重复次数和结束条件。无需为了形式要求得到百分之百复现才允许分析。

若唯一复现条件需要用户环境，给出准确缺少的操作、脱敏日志或权限。已观察到且可以修复的独立问题继续完成；禁止因为一项无关未知冻结所有工作。

## 区分环境故障与产品缺陷

依赖未安装、服务未启动或凭据缺失时，在实际配置与环境里修正。不要向产品加入一个吞掉全部异常的 fallback 来掩盖环境问题。外部服务确实会暂时不可用时，按产品操作语义决定重试、显式失败或恢复。

## 相同根因批量修正

单条和批量入口都读取同一到期约定，修正相等边界时检查共享规则及真实消费者。生成代码有误就改生成来源。状态模型缺少必要区分，就修正模型与调用者；禁止继续沿每个症状写补丁。

## 调试结束后

保留已经确认的原因与当前代码决定，清除临时断点、调试导出和试验文件。尚在使用的临时材料留在仓库外或已忽略位置，提交只保存正式实现和有持续用途的回归。继续原功能尚缺的入口和使用路径。用户没有要求事故报告时，交付修复及有用结果即可。
