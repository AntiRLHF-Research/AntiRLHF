# 领域建模

## 从业务活动找到实体

读取真实操作、现有数据和产品术语。识别哪些对象有持续身份，哪些只是一次输入或呈现结果。确定对象由谁创建、怎样改变、何时消失、谁观察其状态。避免仅按数据库列或某个 API 的 JSON 字段复制领域模型。

同一实体出现多个内部版本、到处做字段转换、几个模块都能修改相同状态，是需要重整的信号。先找到共同语义，再决定哪些表示应合并。不同业务生命周期和外部协议的表示留在相应边界。

## 把规则交给实际所有者

找出每条不变量及其依赖数据，例如发布条件、取消后的效果、数量约束和任务状态。规则放在拥有该变化的模块，所有入口调用它。禁止 API、CLI、后台执行器各维护一套权限或状态判断。

选择聚合范围时看一次业务改变需要哪些状态保持一致。需要同一事务保护的变化放在同一工作单元，跨边界协作用显式操作与事件。具体做法见 [状态与不变量](references/state-and-invariants.md)。

## 设计正式内部契约

让操作表达业务意图，输入采用当前正式数据类型，输出包含调用者需要的成功或领域失败。对重要状态使用明确类型和转换操作，减少任意字符串及含义冲突的可空字段。边界负责格式解析与协议映射，领域负责业务判断。

同一实体的多个可变副本收敛到唯一修改权。读取视图可以针对页面或查询组织，更新仍回到正式操作。禁止在新模型外再造一个 CanonicalBridge，继续维护原来的多套规则。

## 用具体场景完善模型

沿成功、冲突、重复请求和取消等实际操作推演状态。每个场景问当前所有者怎样决定、哪些数据一起改变、观察者会看到什么。只处理本产品涉及的失败，不填充想象中的全部状态机。

领域模型由真实语义决定，测试在公开行为处观察它。禁止为了方便 Mock 拆出无业务用途的接口。类型和操作示例见 [模型收敛与迁移](references/model-and-migration.md)。

## 迁移全部实际消费者

修改模型定义后迁移生产者、服务、后台任务、存储边界和展示者。内部开发模型没有兼容承诺时直接替换，连同旧转换、枚举和专属测试删除。真实持久数据按现有数据情况迁移，现存公共协议在其边界保留转换。

领域结构应使同一规则只有清楚的决定位置，调用者能依赖该契约完成工作。交付设计时写清这些契约；实现任务继续让真实入口使用它们。

设计审批和编辑并存的实体时，读取[文档版本与审批](references/revision-approval.md)，区分对象身份、内容版本和独立状态，避免用布尔字段掩盖业务冲突。
