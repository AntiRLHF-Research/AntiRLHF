# 外部操作：结果、重试与用户恢复

## 教学场景

客户端提交一项远程生成任务，提供方已接收请求，但返回途中连接断开。旧包装器捕获所有异常并自动再提交，产生重复任务和费用。另一个页面把所有失败写成“网络错误”，用户反复点击重试。

正式契约需要表达操作结果，以及调用者可以采取的下一步。共享请求库负责连接、超时、取消和响应读取；提供方适配负责把外部协议转换成当前应用语义；业务服务决定重试、查询原任务还是请用户修改输入。

## 三种失败分别处理

| 观察到的事实 | 所有者作出的判断 | 用户或调用方的动作 |
| --- | --- | --- |
| 提供方明确拒绝参数 | 输入需要修改 | 保留输入，指出对应字段 |
| 读取已有任务状态时暂时连接失败 | 本次读取失败 | 按已定读取策略稍后重试 |
| 创建请求发出后连接中断 | 提交结果未知 | 按请求身份查询或使用提供方幂等协议恢复 |

HTTP 状态码留在适配边界，业务状态使用稳定类型或现有领域异常。底层超时可以保留为 `cause` 供日志诊断，不要求每层重新包一遍同样错误。任何重试都要考虑操作副作用和已完成部分。

## 利用提供方已有语义

若提供方支持幂等键，在首次提交前保存请求身份，同一操作恢复时使用相同键。提供方要求同时校验请求内容时，保留原参数；相同键被另一份内容重用应返回冲突。若提供方只支持查询任务，就保存已知任务 ID 并查询原任务。

两项能力都缺失时，业务服务报告“提交结果待确认”，保留可核对的信息。不要用通用重试装饰器隐式制造第二笔操作。用户决定再次提交时，界面清楚表达这是一项新操作。

## 流式结果的生命周期

流式读取中，响应、连接和下游消费者共同参与生命周期。复用库的上下文管理器，例如 HTTPX 的 `AsyncClient` 和 `client.stream()`；客户端由应用生命周期创建并关闭，响应由单次流读取范围管理。接口用法见 [HTTPX Async Support](https://www.python-httpx.org/async/)。

用户取消时停止本地消费，关闭响应，将取消传递到负责的任务。远端是否取消由协议决定；远端继续执行的任务要保存身份，允许后续查询。界面区分已收到的部分内容和正式完成的结果。

不要把中途断流的结果直接缓存成完整回答，也不要吞掉取消后把空字符串当成功。已展示部分内容时，保留内容并提供继续查询或重新发起的实际入口。

## 统一所有消费者

让 Web、CLI 和后台调度调用相同业务操作。各自只映射展示形式：Web 展示恢复按钮，CLI 输出结果身份和退出状态，后台任务按明确策略安排后续查询。删除三套独立重试和字符串匹配逻辑。

通过一次正常操作和此前真实失败的恢复路径检查接线。若测试只能调用包装器内部私有方法，回到公开业务操作检查接口形状。功能完整后继续产品主线。
